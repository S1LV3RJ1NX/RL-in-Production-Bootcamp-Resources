We have now built three things: a code-fixing agent on a laptop, a coding agent trained for real on cloud GPUs, and a terminal agent that learns to predict the computer's replies. On the surface they could not look more different — three models, three problems, three piles of machinery. But underneath they are the *same move*, done three times. This chapter pulls that single thread through all three, and shows why this one idea is quietly changing how software gets built.

Here is the thread, in one sentence: **nobody hands the machine the right answer; a real environment grades the machine's own attempts, and reinforcement learning nudges it toward the ones that scored better.** That is it. Everything else — the laptop, the H100s, the terminal — is a variation on that one theme.

## The one loop, three times

Cast your mind back to the very first idea in this book: **the tests are the teacher.** We never sat down and wrote out the correct code for the machine to copy. We handed it a problem, let it try, and let something in the world — the tests — say *pass* or *fail*. That verdict was the entire teaching signal. [[sn: This is the deep reason code is such fertile ground for learning machines. For most tasks — "write a good essay," "design a nice poster" — there is no button that returns *correct* or *incorrect*. Code is unusual: a test gives you a crisp, automatic, unarguable grade, for free, forever.]]

Every one of our three projects is that same loop. The learner writes something. An **environment** — a piece of the world that runs the attempt and reports back — grades it. The grade becomes a **reward** (a single number saying how good the attempt was, usually `1.0` for pass and `0.0` for fail). And **GRPO** ([Group Relative Policy Optimization](grpo-learning-from-a-group.html), the trial-and-error learning rule all three share) uses those rewards to make the good attempts more likely next time. The only thing that changes from project to project is *what the environment is*.

Look at the swappable slot in the middle of that figure. That is the whole story of this book. Project one plugs in a tiny bank of laptop tests. Project two plugs in the visible tests of real programming problems. Project three plugs in an entire terminal. The loop around it is identical every time.

[[note: aha || If you remember one thing from this whole book, remember this: **the environment is the teacher, and the reward is what it says.** We never wrote an answer key. We built a world that could grade attempts, and let the model teach itself against it — three times, at three scales.]]

## Three projects, side by side

It helps to see all three laid out at once. Every number here is real — modest, honest, and worth trusting precisely because it is not inflated.

| Project | The environment | The reward | Model & scale | Headline |
|---|---|---|---|---|
| **Mini-SWE-RL** | `CodeFixEnv` — a tiny gym on a laptop | tests pass → `1.0` else `0.0` | Qwen2.5-Coder-1.5B, one MacBook, ~30 min | **66.7% → 73.3%** |
| **Agentic RL** | MBPP+ visible tests on real problems | visible tests pass → `1.0` else `0.0` | Qwen2.5-Coder 0.5B–7B, Modal H100s | 0.5B: **44 → 51**, **14 fixed** |
| **ECHO** | a real, stateful terminal | tests pass → `1.0` else `0.0`, plus a "predict the reply" training job | Qwen3-8B / 14B, Modal sandboxes | ECHO **≈ doubles** GRPO |

Read that table top to bottom and the pattern jumps out. The reward column is almost the same sentence three times: *did the checks pass?* The environment column grows from a toy, to real Python problems, to a live terminal. The scale grows from a laptop, to rented GPUs, to bigger models. But the loop never changes. [[sn: ECHO keeps the same pass/fail reward but adds one extra *training job*: predict what the terminal will print back. That is not a different idea; it is a clever *second* use of the same "let the environment grade you" principle. The terminal's real output is the answer key for the prediction, so again, nobody hand-labels anything.]]

Let us walk the three quickly, because the differences make the sameness convincing.

**Project one — the laptop.** The environment `CodeFixEnv` hands the model a buggy function, runs the tests on its fix, and returns `1.0` if all pass else `0.0`. A **1.5-billion-parameter** model (1.5 billion tunable numbers inside) on a single MacBook, trained for about **30 minutes**, climbed from **66.7%** to **73.3%** on its puzzles — and solved **7** it had never solved before. The environment fit in a file; the loop was the same loop.

**Project two — the cloud.** Here the puzzles are real: **MBPP+**, a bank of small Python problems, each with a few *visible tests* the reward is allowed to see. Same reward rule, same GRPO, but now running on rented **H100 GPUs** through Modal. We tell the story of the smallest model, the **0.5B**, precisely because it starts lowest and has the most room to show learning. It went from solving **44** of 100 held-out tasks to **51** — and the honest framing is the one worth repeating: *of the tasks it was failing, RL taught it to solve 14.* Not a fireworks display. A real, checkable gain. Every one of those fixes is a small, human bug the model learned to correct on its own:

**Project three — the terminal.** Now the environment is not a test file but a whole **terminal** — a text window where the agent types commands like `ls` and `python test.py` over many steps to fix a bug or configure a tool. The benchmark, **TerminalBench-2.0**, is exactly **89** such tasks. ECHO's twist is to add a small second job — predict what the terminal will *print back* — so the agent learns how the computer behaves as a free side-effect of learning to act. [[sn: For that free bonus to actually do anything, the terminal's output tokens must sit *inside* the model's own response, so it is genuinely predicting them. A naive setup where the output only lands in the next prompt makes the whole ECHO loss silently do nothing — a reminder to always check that your clever extra term is actually firing.]] The absolute scores are small handfuls out of 89, so we do not sell them as a leaderboard win. The trustworthy claim is the controlled one: with everything else held identical, adding that one extra loss term (`λ = 0.05`) makes ECHO **roughly double** GRPO's score.

[[note: production || The very same GRPO loop powers **DeepSWE**, an open coding agent that trains a 32-billion-parameter model on 64 H100 GPUs for six days and jumps from **42.2%** toward **~59%** on real GitHub bugs. Our three projects are miniatures of that exact machine — the same algorithm, the same "tests are the teacher" reward — shrunk down so you could watch every gear turn.]]

## Why this quietly changes everything

Step back and notice what we never did. We never wrote an answer key. Not once, across three projects, did a human sit down and hand the model the correct code and say "copy this." That is the shift, and it is bigger than it looks.

For most of computing's history, teaching a machine meant *showing it the answers* — thousands of labeled examples, each one a human saying "here is the right output." That is expensive, slow, and it caps the machine at human patience. These three projects escape that cap. Because software has **checkable goals** — a test that returns pass or fail with no argument — the machine can generate its own attempts, grade them against reality, and improve on *real work* with no human answer key in sight. [[note: metaphor || Think of a student who can only learn from a graded worksheet the teacher hands back, versus one who has a calculator that instantly checks any answer they invent. The first is limited by how many worksheets get made. The second can practice forever, alone, and keep getting better. Tests are that calculator for code.]]

Pair a checkable goal with trial-and-error at scale and you get something new: software that can help improve itself. Give a model bugs and their tests, and it grinds toward fixing them the way a person practices — try, check, adjust — but tirelessly, across thousands of problems at once. The laptop version proves the idea is not locked inside a big lab. The cloud version proves it scales onto real problems. The terminal version proves it reaches all the way to agents that *act* over many steps.

## Where the honesty lives

None of this is finished, and saying so is part of the point. The gains we measured are real but modest — a few points here, fourteen tasks there, a doubling of small numbers. The hard parts stay hard. A reward that only asks "did the visible tests pass?" can, in principle, be gamed by a model clever enough to satisfy the exact checks without truly solving the problem — a wrinkle we meet head-on in the final chapter. Longer, many-step tasks are harder to grade and harder to train. And running these loops for real is as much a systems problem as a math one: jobs that die when a laptop sleeps, engines that sit idle and look crashed. Real machine learning is messy, and we have not hidden the mess.

But the thread holds, all the way through. Three projects, three environments, one idea: build a world that can grade attempts, and let the model teach itself against it. In the last chapter we ask where this goes next — the harder rewards, the whole repositories, and the agents that carry a world model everywhere they go.

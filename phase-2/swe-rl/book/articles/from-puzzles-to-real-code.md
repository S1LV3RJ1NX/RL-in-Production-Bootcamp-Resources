So far we have watched a model teach itself to fix bugs on a laptop — small puzzles, thirty minutes, a modest climb. That was the proof that the machinery works. This chapter takes the same machinery off the laptop and points it at *real* programming problems, run for real on cloud computers with serious hardware. This is the workshop's research project, and it is where a quiet, important question finally gets an honest answer: not just "did the model pass the check?" but "did it *actually* solve the problem?"

## From invented puzzles to real problems

The puzzles in project one were hand-written by us to teach a specific bug — a closure trap here, a floating-point gotcha there. Useful, but a little artificial. For project two we wanted problems we did not author ourselves, drawn from a public collection that many researchers use so results can be compared. That collection is **MBPP+** (a benchmark of **378** real small Python programming problems, pronounced "em-bee-pee-pee-plus"). A **benchmark**, by the way, is just a fixed set of problems everyone agrees to test against — like a standardized exam that lets you compare one student to another fairly.

Each problem in MBPP+ is small and self-contained: "write a function to find the volume of a triangular prism," "write a function to sum the cubes of the first n even numbers." Plain, honest programming, the kind you would give a first-year student. Nothing invented by us — just real tasks with a known right answer.

## The three parts of one MBPP+ task

Here is the part worth slowing down for, because the whole chapter turns on it. Every MBPP+ problem comes in three pieces, and the difference between two of them is the big idea.

The first piece is a **prompt** — a plain-English instruction telling the model what to write, like "write a function to find the volume of a triangular prism." The second piece is a small handful of **visible tests** — automatic checks the model is *allowed to see and is graded on*. [[sn: In MBPP+ these visible checks are the original benchmark's "base" asserts — usually just a few per problem. Few enough that a model can sometimes wriggle past them, which is exactly the tension this chapter is about.]] The third piece is a larger set of **hidden tests** — the "plus" suite, a much bigger pile of checks the model *never sees and is never trained on*. These are the honest ground truth. There is also a **gold reference** — the known-correct solution — kept aside so we can always tell what "right" really looks like.

At the top, a black rounded card labeled "PROMPT" with a purple handwritten line: "write a function to find the volume of a triangular prism". A blue arrow labeled "the model reads this and both test sets" points down to a small model icon in the middle. Below the model, split into two zones. A dashed takeaway box at the bottom in black: "the model optimizes the visible few; the hidden many tell us the TRUTH". || One MBPP+ task has three parts: a plain-English prompt, a few visible tests the model is graded on, and a curtain of hidden tests it never sees — the honest judge of whether it really solved the problem.]]

Why keep two sets of tests? Because they answer two different questions. The visible tests are what the model is rewarded for during training — they are the teacher it hears. The hidden tests are the examiner it never meets. If the model's fix passes the visible tests *and* the hidden tests, it genuinely understood the problem. If it passes the visible ones but fails the hidden ones, it only satisfied the few checks in front of it — it faked its way through.

[[note: metaphor || Think of a student cramming for an exam from three sample questions the teacher handed out. If the real exam contains those exact three, a good memorizer scores full marks while understanding nothing. The visible tests are the sample questions; the hidden tests are the surprise exam. Only the surprise exam tells you who actually learned.]]

This split is why "did it really solve it?" finally has an honest answer. In project one, the tests the model trained on and the tests we scored it on were the same, so a passing grade and true understanding looked identical. Here they are deliberately separated, and that separation quietly reveals something we must be careful about: a reward based only on the visible tests can, in principle, be gamed by a clever enough model — a wrinkle we will save for the final chapter and leave alone for now.

## The same algorithm, a bigger stage

The learning method does not change one bit from project one. We still use **GRPO** — the algorithm that lets the model try a problem several times, scores each attempt, and nudges it toward the attempts that beat the group average. (If that sentence went by fast, it is unpacked gently in [GRPO](grpo-learning-from-a-group.html).) The **reward** — the single number saying how good an attempt was — is still binary: `reward = 1.0` if the visible tests pass, `0.0` if they do not. Tests in, a number out, exactly as before.

Dashed takeaway box in black: "train on the visible few; judge on the hidden many". || The training loop is identical to the laptop project — model, tests, reward, nudge — with one crucial addition: the hidden tests sit outside the loop and are used only to grade honestly at the end.]]

Two things *do* scale up. First, this training ran on real cloud hardware: **Modal**, a service that rents you a **GPU** (the specialized chip that makes model training fast) and runs your code on it. Specifically an **H100**, a high-end data-center GPU — far beyond a laptop. Second, we tried three model sizes from the same family, **Qwen2.5-Coder** at **0.5B**, **1.5B**, and **7B** parameters (the "B" is billions of tunable numbers inside the model; more of them means a bigger, more capable, more expensive model).

Fitting a 7-billion-parameter model onto a single GPU is a squeeze, and the trick that makes it possible is **LoRA** (short for a method that freezes the huge model and trains only a small set of extra "adapter" weights bolted on beside it). Instead of adjusting all seven billion numbers, you adjust a few million — enough to steer the model, small enough to fit. [[sn: LoRA stands for "Low-Rank Adaptation." You do not need the math to use it: the picture is a big frozen block with a small trainable dial clipped onto it. The dial does all the learning.]]

## Which model tells the best story

You might expect us to show off the biggest model. We do the opposite, and the reason is honest. The 7B model already solved about **84%** of the tasks *before any training at all* — it starts so near the top that there is barely any room left to climb, and a before/after picture with almost no "before-to-after" gap teaches nothing.

The 0.5B model is the star of the story precisely because it starts the lowest. Low start, lots of headroom, a clear climb to watch. This is a real modeling lesson, not a marketing choice: if you want to *see* learning happen, pick a model with room to grow.

[[note: confusion || A natural assumption is "bigger model, better demo." For teaching, the reverse is often true. A model already near the ceiling has no visible room to improve, so RL looks like it did nothing. The smallest model, with the most room, gives the clearest before/after — even though it ends up less capable overall.]]

## The result, told plainly

On held-out tasks — problems set aside and never trained on — the 0.5B model went from solving **44 out of 100** to **51 out of 100**. The learning curve rises sharply in the first steps, from about **0.44** up to roughly **0.55–0.61**, and then flattens: the honest "learns fast, then holds" shape. It trained for **80 steps** on the H100.

The honest headline is not a giant leap but fourteen specific tasks that flipped from failing to passing.]]

The most honest way to say what happened is not to wave a big aggregate number around. It is this: **14 tasks flipped from fail to pass.** Of the tasks the model had been failing, reinforcement learning taught it to solve fourteen. That is a real, modest, verifiable improvement — and the modesty is the point. We are not claiming a miracle; we are showing that the same simple loop, pointed at real problems, genuinely teaches a small model to write correct code.

One of those fourteen makes the whole idea concrete. Asked to find the volume of a triangular prism, the model at first wrote the formula for a *box* — it forgot that a prism is half a box.

[[fig: Two hand-drawn code cards side by side, titled in black "one of the 14: find_Volume". It passes the hidden tests too, so it is a genuine fix.]]

And here is the reassuring part: those fourteen fixes are real, not test-shaped tricks. We checked each "after" against the *hidden* tests too, and they pass there as well — so the model did not merely satisfy the visible few, it actually solved the problems. [[sn: When curating these examples we caught two "fixes" that were fakes — the model's function was already correct and only "failed" because it had appended its own buggy test lines. We caught them by *running the code*. The moral: verify by execution, and trust the hidden tests.]] A public beginner site, `rl-teaches-code.vercel.app`, shows these exact before-and-after examples live.

## Where this leaves us

We have taken the laptop's little loop, pointed it at 378 real programming problems, run it on a rented GPU, and watched a small model teach itself to solve fourteen tasks it had been getting wrong — with a curtain of hidden tests standing by to keep us honest. In the next chapter we lift that curtain on the fixes themselves: the actual buggy lines the model wrote, and the corrected lines it learned to write instead.

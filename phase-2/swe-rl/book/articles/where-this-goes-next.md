We have watched a machine learn to fix bugs three different ways — a small model on a laptop, a bigger one on a rented GPU, and an agent that types shell commands and quietly learns how the computer will answer back. Every one of them rested on the same simple deal: let the model try, let a test say pass or fail, and reward what worked. That deal is powerful, and it is honest to say it is also not finished. This closing chapter is about what is still hard — and where a curious reader like you can go from here.

## The reward is a target, and a clever model aims at it

Start with the thing we have quietly leaned on the whole book: the reward is "did the visible tests pass?" That is what makes learning possible, but it hides a subtle trap. Because the reward is "did the visible tests pass?", a clever enough model can sometimes learn to satisfy those specific checks without truly solving the problem — a mild form of **gaming the reward** (scoring well on the exact grader without actually doing the underlying job). One research direction the workshop is exploring re-grades each attempt on *altered but equivalent* versions of the tests, so an answer shaped to the exact visible test no longer scores — making the reward much harder to cheat.

[[note: metaphor || Imagine a student who somehow gets the exact exam questions in advance. They can score full marks by memorizing five answers without understanding the subject at all. Change the numbers in the questions, though, and the memorizer is exposed while the student who truly learned still passes. A reward built from a few fixed checks has the same weak spot: hitting the checks and understanding the subject are not always the same thing.]]

[[fig: A hand-drawn scene titled "the reward is a target". LEFT, a black box "the task: really solve the bug". RIGHT, a smaller green box "the reward: pass the 3 visible tests". A blue arrow from a small model icon splits into two purple paths pointing at the RIGHT box: top path labeled "honest fix" with a green check, bottom path labeled "test-shaped guess" with an orange squiggle and the red note "passes the 3 checks, still wrong". A dashed orange takeaway box: "the model aims at the REWARD, not the TASK — so making the reward hard to fake is an open problem". || When the grade is a few fixed checks, a clever model can learn to hit the checks without truly solving the problem — an honest open challenge for RL on code.]]

Notice we saw this danger for real. Back in the second project, two "fixes" that looked like wins turned out to be fake — the model's own function was already fine, and it had only "failed" earlier because it appended its own buggy test lines. [[sn: The catch was low-tech and reliable: we *ran the code* and checked it against the hidden tests the model never trains on. When you cannot fully trust the grader, an independent, unseen check is your safety net.]] That is why the featured before/after examples were all re-verified against the hidden tests — so they are genuine fixes, not answers shaped to the exact visible check.

## Real work is many steps, not one function

The first two projects handed the model one buggy function and asked for one fix. Real software engineering almost never looks like that. Fixing a real bug is a *chain* of small moves: read the complaint, search for the guilty file, read some code, run the tests to see what breaks, try an edit, run them again, back up when you are wrong. Each step depends on what the last step revealed.

This is called a **multi-step task** (a job that takes many actions in a row, where later moves depend on what earlier moves turned up), and it is genuinely harder to teach. When a whole ten-minute session ends in a single pass-or-fail reward, the model has to figure out *which* of its many moves deserved the credit — a much murkier signal than "this one fix passed."

[[note: example || Think of baking a cake and being told only, at the very end, "it tasted bad." Was it the oven temperature? The missing egg? Too much salt? One verdict at the end, spread across a dozen steps, is a faint teacher. A one-line fix that passes or fails is a loud one. Longer tasks trade a loud signal for a realistic one — and learning from the faint signal is an open challenge.]]

The third project, ECHO, is our first real taste of this longer shape: its agent solves each task by typing shell commands over many turns, and it is scored on **89 real terminal tasks** where "done" might mean fixing a bug, configuring a tool, or making a test pass — all through the keyboard. That step from one function to a full session of commands is exactly the frontier.

## Whole repositories, not toy puzzles

Our laptop project used **45 hand-written puzzles**; the second used **378** small self-contained Python problems. Both were built so you could see every gear turn. Real codebases are a different animal: thousands of files, tangled dependencies, and a "run the tests" step that only works inside a carefully prepared environment.

[[note: production || The grown-up benchmark here is SWE-bench: real bugs pulled from real GitHub projects, each shipped inside a **Docker** container — a sealed, pre-built copy of the whole project with all its libraries, so the tests run the same way on any machine. The laptop project's tiny `CodeFixEnv` is a miniature of exactly this: it mirrors R2E-Gym, a real environment of **8,100** GitHub problems in Docker. The open agent DeepSWE — same GRPO algorithm you learned — climbs from **42.2%** to about **59%** on SWE-bench Verified. That leap is what "whole repositories" costs and rewards.]]

[[fig: A hand-drawn scale map titled "from puzzle to repository", three rounded boxes left to right joined by blue arrows. Box 1 (black), pale-green fill: "ONE FUNCTION — 45 laptop puzzles, 1 file, tests in seconds". Box 2 (black): "SMALL PROBLEMS — 378 MBPP+ tasks, 1 file each, visible + hidden tests" with a green tag "0.5B model, 44 -> 51 solved". Box 3 (black): "WHOLE REPO — thousands of files in a sealed Docker box, run the tests inside it" with a green tag "SWE-bench: DeepSWE 42.2% -> 59%". Under the arrows, an orange handwritten note growing left to right: "same shape — code, tests, done = pass — just a bigger haystack". Dashed takeaway box: "the algorithm barely changes; the ENVIRONMENT gets much harder to build". || The same task, scaled from one function to a full repository. The hard part of "real" is not new math — it is standing up an environment big and faithful enough to grade the model.]]

The pattern to hold onto: the *algorithm* barely changes as you scale up. What gets hard is the **environment** — building a teacher that can run a real project's real tests, safely and repeatably. That is why so much of real RL work, as we saw, is a systems problem, not a math problem.

## Agents that carry a world model everywhere

The last idea is the one the third project was built to explore, and it points furthest ahead. An agent that only knows how to *act* is flying blind between moves. An agent that also carries a **world model** — an internal sense of what will happen next when it does something — can look before it leaps.

ECHO's contribution was to grow that sense almost for free. Train the agent to act with GRPO as usual, but add one small extra job: predict what the terminal will print back after each command, reusing the very same forward pass. [[sn: For that extra job to actually do anything, the terminal's reply has to sit *inside* the model's own response, where it is genuinely being predicted — a naive wiring that tucks the reply into the next prompt makes the whole idea silently do nothing. The team verified the extra loss was really firing before trusting any result.]] Learning to predict the computer's replies teaches the agent how the computer *behaves*, as a side effect of learning to act — at a cost of one extra term in the loss, weighted by a small `λ = 0.05`.

[[fig: A hand-drawn wiring map titled "a world model, for free". Center black box "ONE forward pass" fed by a blue arrow from a small terminal window (the commands so far, in purple). Two blue arrows leave the box: top arrow to a black card "ACT — write the next command" (this is GRPO, green tag "the main job"); bottom arrow to a black card "PREDICT — what the terminal will print back" (green tag "the extra job, weight 0.05"). A dashed orange takeaway box: "same pass, one extra loss -> the agent learns how the computer BEHAVES". A small green note by the bottom card: "learning to predict the reply = a world model". || ECHO's idea in one picture: reuse a single forward pass to both act and predict the environment's reply. The prediction habit becomes a cheap world model.]]

Why does that matter for where all of this goes? Because the honest, high-confidence result from ECHO is a *controlled* one: with everything else held identical and only that extra job added, it roughly **doubles** the plain GRPO score in a head-to-head. [[sn: Be careful with the raw numbers. The absolute scores are tiny — a handful of the 89 tasks, like an 8B model moving from **2.70** to **5.17** — and they lean on about **6,000** private training tasks a replication cannot reproduce. So the honest claim is the *relative* doubling in a clean A/B, not a leaderboard trophy.]] A world model is not a bigger algorithm; it is a richer thing for the agent to learn on the way to acting. Carrying that everywhere an agent works — every terminal, every repository, every long task — is one of the most promising roads ahead.

You understand a **checkable task**: code, a failing test, and a definition of done a machine can verify by itself. You understand the [RL loop](rl-in-one-sitting.html) — try, score, nudge. You understand [GRPO](grpo-learning-from-a-group.html), and why the group's own average, not a separate critic network, is the yardstick. You understand an environment as a teacher, where the tests hand back a `1` or a `0` and nobody labels the right answer by hand. And you have watched three real projects turn all of that into models that measurably improved: **66.7%** to **73.3%** on a laptop, **44** to **51** solved tasks on a rented GPU, and a terminal agent that grows a world model for free.

That is not a spectator's understanding. It is enough to open the papers and follow them, to clone [Mini-SWE-RL](https://github.com/RajatDandekar/Mini-SWE-RL) and watch the exact loop from this book run on your own machine in half an hour, and — when a bug or an idea nags at you — to build your own. The tests are the teacher. Go hand a machine a problem, and let it try.
